# ADR 0003 — Bait replaces the generic marker as the core entity

- **Status:** Accepted
- **Date:** 2026-10-20
- **Deciders:** Luis
- **Amends:** ADR 0001 (terminology only; the ownership decision stands)

## Context

MarkCamp v1 started as a GPS tracker for stingless bee bait hives and was later
generalized into an app for marking any point in the field. ADR 0001 and the
repository docs inherited that framing and talk about generic "markers".

In October 2026 the product direction changed: MarkCamp becomes a management app
for stingless beekeepers (meliponiculture). The MVP covers **bait hives only**.
Colonies, splits and their origin come later.

No migration exists yet, so this is the cheapest moment to choose the core entity.
After the first migration and the first real data, renaming or restructuring it
means a data migration, API changes and client changes.

## Options considered

### A. Keep a generic `marker` and add a `type` (e.g. `BAIT`)

- Matches the current docs and ADR 0001 wording.
- Leaves room for other point types (colonies, apiaries, trails) in one table.
- Bait-specific data needs a place to live from day one: nullable columns that only
  apply to some types, a JSON column the database cannot validate, or table
  inheritance. All three add complexity to serve a second type that does not exist.
- Bait history (installation, inspections, capture) does not make sense for a
  generic point, so the generic table would still need bait-only tables around it.

### B. `bait` is its own entity; the generic marker is dropped

- The schema speaks the domain language: a beekeeper installs, inspects and
  captures with a *bait hive*, not a *marker*.
- Every column applies to every row; the database can enforce constraints directly.
- If a future entity (e.g. `colony`) also needs a location, a shared concept can be
  extracted then, with two real cases to design from.

## Decision

**Option B.** `bait` is the core entity of the MVP. There is no generic `marker`
table and no `type` discriminator.

ADR 0001 remains in force with "marker" read as "bait": a bait belongs to a project,
and access is decided exclusively by `project_members`.

## Consequences

### Positive

- Schema, API and code use the same vocabulary as the users.
- No speculative abstraction; constraints live in the database.
- Each future entity (e.g. `colony`) gets its own table and its own ADR when it
  enters scope.

### Negative

- If several entities end up sharing the same shape (location, project, notes),
  some duplication will appear and a shared concept will have to be extracted later.
  Accepted: extracting an abstraction from two real cases is cheaper than undoing a
  wrong one that already holds data.
- ADR 0001 and ADR 0002 keep the word "marker" in their text, which reflects the
  framing at the time they were written.

### Derived rules (non-negotiable)

1. ADR 0001's rules apply to `bait` unchanged: `created_by` is never authorization,
   and every bait query goes through the single project access check.
2. ADR 0002 applies: `bait.id` is a UUID v7 generated by the application, with no
   database default.
3. How bait history is modeled (status column vs. event table) is a separate
   decision, recorded in its own ADR before the bait migration is written.
