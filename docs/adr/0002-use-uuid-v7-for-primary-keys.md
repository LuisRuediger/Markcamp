# ADR 0002 — Use UUID v7 for primary keys

- **Status:** Accepted
- **Date:** 2026-09-22
- **Deciders:** Luis

## Context

MarkCamp is offline-first. Markers are created on a phone in the field, often with
no signal. The client must assign an identifier the moment a record is created,
because the sync queue needs to reference that record (create, then edit, then
possibly delete) before the server knows it exists.

This decision affects the primary key of every table and is expensive to change
once data exists, so it must be made before the first migration.

## Options considered

### A. Auto-increment `bigint`

- Compact, readable, natural ordering.
- Only the database knows the next value, so an offline client cannot generate one.
- Would require temporary client IDs plus a mapping step after sync. That kind of
  reconciliation logic was a major source of sync bugs in v1.

### B. UUID v4 (random)

- Generated by the client with no practical risk of collision. Solves offline creation.
- Fully random values land in random positions of the primary key index, causing
  fragmentation over time. Irrelevant at MarkCamp's scale, but a known cost.

### C. UUID v7 (time-ordered)

- Generated by the client, no practical risk of collision. Solves offline creation.
- The leading bits are a timestamp, so new IDs are appended near the end of the
  index, similar to auto-increment.
- Sorting by ID approximates creation order.

## Decision

**Option C: UUID v7** for all primary keys.

The database column type is `uuid`. IDs are generated by the application: by the
client for records created offline, and by the backend for records it creates.

## Consequences

### Positive

- Offline creation works without any ID reconciliation step.
- Index behavior close to auto-increment.
- Same approach for every table, no special cases.

### Negative

- 16 bytes per key instead of 8, and IDs are harder to read in logs.
- The creation timestamp is embedded in the ID and can be extracted by anyone who
  sees it.

### Derived rules (non-negotiable)

1. No database default for primary keys. Postgres's built-in `gen_random_uuid()`
   generates v4, and a default would silently mix formats.
2. The server accepts client-generated IDs, so it must treat them as untrusted input:
   validate the format, and reject a create whose ID already exists. A create must
   never overwrite or "upsert" an existing record, especially one in another project.
3. IDs are not secrets. Authorization never relies on an ID being hard to guess
   (see ADR 0001: access is checked through `project_members`).
